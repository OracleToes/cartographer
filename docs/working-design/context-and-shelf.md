# Working design: universal references, books, schemas, and collapse memory

**Status:** Stage 3's file-shelf lifecycle follow-up and Stage 4 implementation are complete. Stage 5 implementation is complete: compact schema selection, strict provider routing, branch-specific projections, local execution guards, retry/restart recovery, success cleanup, and schema budgeting are in place. Acceptance verification remains deferred to Stage 8; do not run tests unless the user explicitly asks in that conversation. Live endpoint enforcement remains unverified.

## Confirmed intent

1. **Give durable agent-known entities usable identities.** Project files and brain entities have durable IDs. Durable session conversations and transcript entries use the IDs supplied by `pi-durable`; external shelf targets and their snapshots use temporary IDs, and external IDs may be reused because they resolve to their current target. Directories do not need IDs because the tree in the state block describes them. Live shell windows and running processes have operational IDs in the state block, but are not bookkeeping targets for `book`.
2. **Separate shelf identity, backing snapshot, and attention.** A shelf item has a stable ID while it is shelved. For a project file, keep a full backing snapshot as a real file under `.atlas`, but put only the selected range in active context. If the source disappears, the same shelf-item ID resolves to the snapshot so the selected range can still change. External snapshots and their temporary IDs exist only for the shelf item's lifetime; unshelving burns the ID and discards the snapshot. If the system cannot read and snapshot an item, reject the shelf add without changing the shelf.
3. **Apply the context token cap only to what enters the model's context.** The cap covers rendered ranges and other context content, not full backing snapshot files. The user prefers no separate shelf-item size cap; unreadable or unsnapshotable targets are rejected. A source change is shown as a diff in the state block; at collapse, refresh the backing snapshot from a still-existing source and reset the comparison baseline. If the source is gone, retain the snapshot.

4. **Load other tool schemas on demand.** A full schema for a tool should be brought into the current context only when that tool is about to be used, rather than keeping every full schema in every request. Keep it available through validation; after a successful call, remove the temporary schema material but retain the successful exact call pattern and result as an example.
5. **Collapse should organize memory, not just trim it.** As a session grows, cluster useful chat and context into structured blocks corresponding to the user's visible areas: chat, atlas, ledger, plan, requests, tree, books, shells, thinking, notes to self, and tool results. Treat the clusters as a loose stack rather than a fixed-order outline: order or regroup by recency, and only reorganize as deeply as needed. Keep the newest tail relatively raw/frayed. Preserve exact information where needed and retain links/provenance so a summary does not replace a source of truth.
6. **Centralize configuration-like values throughout the codebase.** Avoid scattered magic numbers, fixed control words/strings, default choices, thresholds, flags, and toggles; values such as `control: { terminate: true }` in `src/tools/chat.mjs` belong in the central configuration surface. This does not mean mechanically moving ordinary local implementation variables. Preserve behavior while doing the broad configuration sweep.
7. **Use one tagged row model and a shared entries engine.** Preserve composed rows generated from task/tool history and curated rows independently selected and editable as distinct species in one understandable model. The agent and user have the same row operations. Persist operations immediately; `when: now | next-boundary` controls only when the active context reflects them. `now` takes effect after the current safe tool call/round; `next-boundary` takes effect at the next collapse/rebuild. The state block reports pending visibility differences, including additions, edits, and removals. An explicit collapse finishes the current tool call/round safely and starts the next model request from collapsed context. Reports are composed rows referencing separate full-report content, preserving IDs and recall/fold/archive/unarchive/delete behavior without `REPORT`-pattern dispatch in the shared operations layer. Use the shared entries engine for plan CRUD through specs-with-hooks; keep plan authorization logic hand-rolled and separate.

8. **Make `book` the universal, reference-driven operation tool.** `book` is the common interface for working with any supported agent-known entity. The call selects a target/book and a standardized operation; a reference identifies the specific entity. Use shared operation language and behavior where semantics match, with explicit type-specific capabilities rather than inconsistent special workflows or verbs stretched beyond their meaning. The schema is comprehensive because the tool has broad responsibility: preserve descriptions and exact validation behavior, and load the relevant full schema live/on demand rather than stripping useful guidance to make it smaller. Every entity must be resolvable through a shared reference interface; the shelf is a first-class target/operation, not a pair of context-only `shelve`/`unshelve` exceptions. The required `target`/`action` shape and one-operation-per-call direction are settled; the exact reference envelope and remaining lifecycle details stay gated below.

## Confirmed direction

- Give every tool and exact schema version its own reference; schema lookup is an operation on those references. Keep the universal `book` contract/schema available, and load the selected entity/action's relevant full schema when needed. Do not frame shelf as a separate special tool with its own isolated schema.
- **Store namespace (confirmed):** the persistent namespace belongs to the Cartographer brain-store instance, not a Git branch or provider conversation. A backup/restore preserves it. An independent clone/fork gets a fresh namespace and its internal references are rebound, retaining the source namespace as fork provenance. Worktrees sharing one `.atlas` store share its namespace. Do not guess clone intent from an arbitrary filesystem copy.
- **`.cartoignore` (confirmed):** it filters ambient discovery (tree/list/search/suggestions and automatic context), but does not remove file identities or block an explicit shelf add by reference. It is not an access-control or secrecy boundary. Every in-scope project file remains referenceable; `book shelf add` is the explicit operation that exposes the selected content to the model. A reference by itself does not load file content.
- **`book` shape (confirmed direction):** `target` and `action` are both required, with one operation per call. `book` is the model-facing replacement for separate content-facing `read`/`write`/`edit` tools; there is no target-less `book edit`. The target selects the domain (for example `file`, `message`, or first-class `shelf`), and the action is validated against that target's capabilities. Out-of-brain targets dispatch through a short focus; brain targets can be updated directly. Shelf `add` resolves a target reference and selection; shelf `remove` takes the temporary shelf-placement ID, distinct from the durable target ID.
- **File identity (confirmed):** use Durable `DocumentId` for a Cartographer-managed catalog record that maps a stable file identity to its current project-relative path and provenance. Durable's API does not itself bind a document ID to a filesystem file or observe external renames. Preserve identity when Cartographer observes a rename/move or the user explicitly rebinds it; treat an unobserved move as deletion plus a new file. Copies and delete/recreate get new IDs; deletion retains a tombstone/provenance record. Ordinary edits preserve the entity ID and create a new content version. This does not pretend `DocumentId` supplies filesystem lifecycle tracking.
- **Initial catalog scope (confirmed):** include all persistent agent-known brain records, as well as the already listed project files, reports, schemas, messages, tool calls/results, and prompt content. Operational runtime state remains outside the `book` identity catalog. `book` capabilities remain type-specific; universal identity does not imply that every entity supports every mutation.
- **Existing and Durable IDs (confirmed):** keep existing ledger, plan, atlas, report, and curated-row IDs; map them into the universal reference rather than renumbering them. Reuse Durable IDs for Durable-owned conversations and entries. Address a model-issued tool call by its owning conversation plus parent assistant `EntryId` and provider call ID; retain its Durable tool-task ID and result `EntryId` as linked provenance. A nested tool call uses parent `TaskId` plus parent call ID and nested key, with its result in the parent's nested-call document. Retries/forks are distinct occurrences unless Durable identifies the same event.
- **Reference/version and conflict behavior (confirmed direction):** use `{ namespace, kind, id, version? }`; preserve entity IDs across edits and pin exact versions where needed. Edits/removals use an expected-version/precondition and reject stale writes rather than silently overwriting. Replaying the same durable operation is idempotent; a new `add` creates a new entity unless that target explicitly defines a natural-key upsert.
- **Shelf resolution (confirmed):** mutable/non-file targets resolve to their live current content while they exist; if missing or inaccessible, report that state explicitly and do not silently fall back to an old snapshot as if current. This does not replace Stage 3's explicitly retained file-shelf snapshot behavior. References alone do not expose content; an explicit shelf add does.
- **Message edit/forget (confirmed as soft-forget):** editing a user/assistant chat message removes it and its derived copies from future agent-visible context, summaries, and ordinary recall; the agent sees only a generic success confirmation. Durable's raw append-only transcript remains stored and is not claimed to be erased. Tool-call/result and system/compaction entries remain operational history under the selected chat-only scope. This is a deliberate exception to ordinary agent recall, not physical data deletion.
- **Long-term retention (open design):** soft-forget does not reclaim Durable transcript storage; pi-durable compaction also leaves old entries stored. Keep active-context forgetting, durable memory books, and physical storage pruning as separate concepts. A future prune/retention mechanism needs a supported, safe storage rewrite or backend API; do not silently mutate Durable's append-only internals.
- For a selected tool, make its precise full schema available both in the active context and in the provider-facing `tools` payload for that request. Validate the resulting call locally as well. After a successful call, remove the temporary schema material from subsequent context and retain the successful exact call pattern and result as an example. This is intended to make complex calls more reliable while keeping the ordinary prompt small; local validation still does not guarantee the model will initially generate a valid call.
- Use one universal typed-reference catalog, with shared resolvers for files, reports, schemas, messages, tool calls/results, prompt content, and all persistent brain records. `book` operations act on those references through one capability-aware contract; shelf is a first-class way to keep references and their selected live content in view, not a separate per-kind workflow. A schema reference resolves to the exact schema version/content used; report references retain links to their separate full bodies unless explicitly hard-forgotten.
- `shelfTokens` caps only material rendered into model context (for example, the selected range), not the full backing snapshot file in `.atlas`. A schema loaded temporarily for a tool call does not count as persistent context content. Reserve enough working-context room for the largest full tool schema; verify deterministic collapse/headroom against actual context-budget behavior before implementation.
- For an incomplete or invalid submission, return a clear, actionable error and rely on the model to recover; do not design a separate recovery workflow in advance. The user will report concrete failure modes if this proves insufficient.
- **One-agent/focus model (confirmed):** there is one Cartographer agent and one durable brain. A task is the agent in a temporary, focused context, not another mind or memory owner; it can keep durable findings in the shared books and atlas, knowing unkept context may leave active context. Only the orchestrating context changes the plan. Focus state and purpose are shown in a refreshed state block. Out-of-brain `book` operations invoked by the orchestrating context dispatch as short, atomic focuses; when already in a focus, perform the bounded operation inline without nesting. `shell` remains focus-only. Existing user-approval and safety gates stay in force.

## Universal reference and `book` contract

Universality is the architectural goal, not a prompt-size optimization or a shelf-only feature:

- Every agent-known entity has an identity/reference. The confirmed scope includes system-prompt content, tools and exact schemas, chat messages, tool calls/results, project files, and brain entities. Directories need no separate ID because the tree describes them. Live shell windows and processes have operational identities in the state block, but remain outside `book`'s bookkeeping operations.
- `book` selects a required target and action on a referenced entity; the intended model includes `book plan add ...` and `book shelf remove ...`. The current implementation still selects only `ledger | plan | books | context`, with shelf mutations hidden as context `shelve`/`unshelve`. Stage 4's proposed schema requires `target` and `action`, one operation per call, so `book edit` without a target is invalid.
- All supported durable entities must be addressable and operable through the common `book` system. Operations share names and semantics where appropriate; a type-aware capability contract defines which operations apply. This does not bypass approval, sandbox, network, project-root, or other explicit safety checks. Confirmed workflow direction: brain-scoped book operations work directly in either context; out-of-brain book operations from the orchestrating context create a short focus, and an existing focus handles one bounded operation inline; shell remains focus-only; only the orchestrating context changes the plan. Whether `wake`/`sleep` stay orchestrator-only is not yet revisited.
- **Durable identity finding:** the linked `@earendil-works/pi-durable` source is version 1.5.2, matching this repository's lockfile. It defines typed `ConversationId`, `EntryId`, `TaskId`, `SubmissionId`, and `DocumentId`. An `EntryRecord` has an immutable `EntryId` and `ConversationId`; a conversation fork records its parent conversation and fork entry. Reuse these native IDs for Durable-owned records rather than minting parallel message IDs. A model-issued tool call is in an assistant entry and is addressed by conversation plus parent `EntryId` and call ID; its execution `TaskId` and result `EntryId` are linked records. Nested `executeTool()` calls instead use parent `TaskId`, parent call ID, and nested key, with results stored in the caller's `NestedCallDoc`.
- Durable's `Session` is the storage-backed scope; its core ID types do not define a separate `SessionId`. The root conversation ID is reserved within a store, and typed numeric IDs are not globally unique by themselves. Universal references therefore need the persistent project/brain-store namespace in addition to the native type and ID. Backups/restores preserve that namespace; an independent clone/fork gets a new one and rebinds internal references while retaining fork provenance. The UUID in `pi.provider` is a per-conversation provider identity, not the store namespace. The pi-durable 1.5.2 `DocumentId` identifies Durable-managed records; it has no built-in filesystem association or rename tracking. The user confirmed the Cartographer catalog adapter and file-move/rebind lifecycle described above.
- Project/brain entities have durable identities. An outside target gets a temporary shelf ID; IDs may be reused because the pointer's present target is the truth. Temporary snapshot IDs and snapshot files last only as long as the shelf item. Snapshot data for a project file lives as a full backing file under `.atlas`, while only the selected range enters model context. A stable shelf-item ID survives a source-file disappearance by resolving to its snapshot instead. Unshelving burns temporary IDs and discards their snapshots. If the system cannot read and snapshot a target, reject the add without changing the shelf.
- `shelfTokens` limits only material actually rendered into model context; it does not cap backing snapshot storage. The user prefers no separate shelf-item size cap. Disk/write failures still need clear error behavior.
- **Updated by the confirmed soft-forget contract:** `book message edit` removes a selected user/assistant chat message from future agent context and ordinary recall rather than rewriting its wording. It returns only generic success and removes derived agent-visible copies, but the raw append-only Durable transcript remains stored; do not claim at-rest erasure.
- Preserve useful schema descriptions and exact validation behavior. The full schema is guidance as well as validation; do not shorten it by discarding useful wording. Continue to verify what compile/provider layers actually preserve before implementing dynamic schemas.

Stages 2–3 are complete within their narrower scope, but their current IDs/references do **not** satisfy universal identity or universal `book` operations. Stage 3's shelf lifecycle follow-up is implemented; the current system remains a typed file/report shelf rather than the universal reference catalog.

## Current behavior observed

- `book` is the top-level tool, but its `book` argument currently selects only `ledger`, `plan`, `books`, or `context`; `ops[].action` is the verb. Shelf is not a first-class selectable target: it is exposed as context `shelve`/`unshelve` actions, and shelf entries are identified by path/reference or `all`, not a universal item ID.
- Stages 2–3 introduced tagged composed/curated rows and typed file/report shelf records. Stage 3's follow-up stores a full text backing snapshot for each shelved project file under `.atlas/shelf/<shelf-id>.txt`; `carto-context.json` keeps the stable shelf-item ID, source/range metadata, and selected rendered view. Only selected/rendered content counts against `shelfTokens`; full backing file size does not. Whole-file display remains line-capped. A missing/unreadable source falls back to the backing file, keeps the same item ID, and is reported in the state block; the selected range can be changed from the snapshot by shelving the same path/range again. Unshelving by ID or path removes the item and its backing file when no shelf still refers to it. Over-budget rendered entries remain shelved but are identified as not shown. This is still not a reference catalog for prompts, schemas, messages, tool calls/results, and all project/brain entities.
- The collapse front block has fixed sections for finished-task records, shelf contents, and the most recent chat up to `chatWindow`. It does not currently cluster older chat into topic/decision summaries.
- **Stage 0 budget trace:** the main and task contexts use `contextWindow * collapseFull / 100` (default 80%) as a near-full trigger, based on the server's reported usage after a response. `engine.sizes()` separately reports a fixed estimate for tool definitions plus the system prompt, but the trigger does not reserve explicit space for a temporarily expanded tool schema. Thus collapse-before-overflow is not yet a guarantee.
- **Stage 0 provider trace:** `openSession()` builds one fixed `wordingTools` list shared by the main agent and task forks. In the installed `@earendil-works/pi-durable` 1.5.2 API, `beforeProviderRequest` is a replacement hook over the provider-specific payload, so it can change the outgoing tool schema for one request without changing the registered tool list. `prepareArguments` runs before ordinary schema validation and execution, so a selected full schema can be checked locally there; retain the existing schema validation afterward. The dynamic payload still changes the provider prompt prefix and needs careful token/prefix handling.
- **Stage 0 collapse finding:** the threshold is based on server-reported usage from a prior response. It does not prove that the next request—especially one with a larger schema—will fit. The maximum schema footprint and a deterministic reservation/trigger policy remain to be calculated in implementation.
- **Stage 0 configuration inventory:** behavior-defining values are distributed across central defaults and many modules, including limits, timing values, schema bounds/enums, fixed control strings, and tool control/replay settings; `terminate: true` appears in several tool/harness paths. The sweep is broader than numeric literals and needs a deliberate migration map. Tests have not been run, per instruction.

## Current action boundaries

- **Current implementation vs. target:** today the orchestrating context cannot call project `read`, `search`, `list`, `write`, `edit`, or `shell` directly; project work runs in a focused context. The intended universal `book` contract replaces the separate content-facing file tools with type-specific book actions, automatically dispatching out-of-brain operations into short focuses. `shell` stays focus-only. This is a workflow mechanism, not a separate agent or memory owner.
- A focus **does not always need a plan item**. In the current implementation, a focus without `item` is read-only (`read`, `search`, `list`) and needs no plan or approval.
- A project mutation must still satisfy the authorized-plan and user-approval rules; the orchestrator alone changes the plan, and either context can update other shared books. An out-of-brain `book` call from the orchestrating context creates one short focus; an existing focus performs the bounded operation inline, without nesting. Do not remove other safety gates.
- By default, approval is on (`yolo: false`) and command sandboxing is on (`bwrap: true`). `/approve p2` approves a specific waiting request; `/approve` authorizes the open change items in the plan as it stands. `/yolo on` bypasses approval while the process runs, but does not remove the plan-item requirement. `/yolo off` restores approval.
- Approval and sandboxing are separate gates. `/bwrap` or `--no-bwrap` controls command sandboxing; a plan item's `network` mark controls whether its change task may use network access in the sandbox. The configured runner may also run commands directly or refuse them if sandboxing is unavailable.
- Current runtime restricts `task`, `wake`, and `sleep` to the orchestrating context and forbids nested focuses. The no-nesting behavior matches the agreed inline execution rule for an already-active focus. Whether `wake` and `sleep` remain orchestration-only workflow controls is still open; keep their current behavior until settled. Preserve approval, sandbox, network, project-root, and undo protections independently.

## One agent, focused contexts, and the forget threshold (core concept)

Cartographer is one agent. A “task” is that same agent focusing on bounded work in a temporary active context; it is not a separate worker or memory owner. The focus knows unkept working context may leave active context, so it can update the shared durable brain before returning. This soft-forget changes what is presented as current context, not the underlying Durable transcript.

- **Shared memory:** focused contexts can update the shared ledger, assessment/practice books, atlas, and context rows while working. Only the orchestrating context can change the plan. The current code enforces this division in `src/tools/book.mjs`.
- **State visibility:** every focused request receives a fresh state block showing the project/brain state and a one-line purpose (`I am <doing something>`). The working context is not hidden from itself; the shared block is not conversation history and is refreshed per request.
- **Forget boundary:** when focus returns, its working conversation can be forgotten; durable book/atlas changes and its report persist. A shelf item named for handoff is added to the focus shelf if absent, then handed on, instead of failing solely because it was not previously shelved.
- **Plan authority and independent safety:** only the orchestrating context changes the plan. That is the context-authority boundary; existing authorized-plan, user-approval, sandbox, network, project-root, and undo protections remain independently. The model-facing content interface is `book`; out-of-brain calls auto-dispatch to a focus, while shell remains focus-only. `wake`/`sleep` availability in a focus is still open; current behavior is preserved until discussed.
- **Automatic focus transition:** out-of-brain `book` operations from the orchestrating context enter a short focus with a one-operation brief and state purpose; if already focused, execute inline. The return-time yes/no brain-review checkpoint then permits only brain-scoped `book` updates before orchestration continues. This dispatch is not a general router for unrelated tool calls.
- **Exact edits:** `read` output separates line numbers from source bytes with `│`. For `edit`, copy only bytes after that delimiter and preserve every space, tab, and line break. If matching fails or indentation is uncertain, inspect bytes with `sed -n 'A,Bp' path | cat -A`; never infer indentation from the line-number prefix.

### Long-term `.atlas` growth (separate from soft-forget)

Inspection of `@earendil-works/pi-durable` 1.5.2 shows committed transcript entries are immutable and append-only through the public API; its compaction summary does not remove older stored entries. Soft-forgetting a message changes what the agent receives later, not the bytes retained in the Durable store. Do not claim storage reclamation from context collapse, message soft-forget, or shelf removal.

Recommendation for discussion: add a separate explicit retention/prune lifecycle that first makes durable knowledge available in books/atlas, then prunes eligible old transcript payloads through a supported Durable export/rewrite or backend erasure API. A future prune should have a preview/dry-run, conservative eligibility rules, preserved store namespace and minimum ID/provenance tombstones, an atomic recoverable rewrite/backup, and clear size accounting; it should never delete arbitrary `.atlas` state. The age/size thresholds, whether old raw conversations remain recoverable, and whether pruning is user-triggered or automatic are unresolved. Do not mutate Durable's internal storage tables ad hoc.

### Proposed contract to review

1. **Reference envelope (confirmed):** `{ namespace, kind, id, version? }`. `namespace` is the persistent brain-store namespace; `kind` selects the resolver/capability spec; `id` is that kind's native or catalog ID. `version` pins exact content when needed; otherwise lookup explicitly means “current.” A path, label, or provider call ID alone is never a durable cross-entity reference.
2. **Identity vs. version (confirmed):** an entity keeps its identity when its content is edited; an immutable revision/version records exact content. Preserve existing domain IDs for ledger, plan, atlas, report, and curated-row records, mapped into the envelope rather than renumbering them. Use Durable-native IDs for Durable-owned conversations and entries. Represent file identities with Cartographer-managed catalog records keyed by Durable `DocumentId`; keep path, content revision, and provenance as mutable metadata, not identity.
3. **File lifecycle (confirmed):** an observed move or explicit user rebind updates the path on the same file identity; an unobserved move is delete/tombstone plus a new identity; copy and delete/recreate get new identities. Ordinary edits retain the file identity and create a new content revision. Preserve tombstones/provenance so old references resolve to `deleted`, not to an unrelated file that later reuses the path.
4. **Transcript/tool-call links (confirmed):** retain each Durable ID in its owning namespace. A tool call is addressed by its owning conversation and assistant `EntryId` plus the provider call ID; its Durable tool-task ID and separate result `EntryId` are linked provenance, not substitutes for that composite address. Retries and forks are distinct occurrences unless the Durable store proves they are the same event. Do not infer identity from tool name or arguments.
5. **Resolver result:** return the reference and type, requested/resolved version, source/provenance, supported actions, and a status from `live | stale | deleted | inaccessible | unsupported | oversized`. Resolution alone does not load content into the model; an explicit inspect/read or shelf-add does. Never return stale snapshots as current for mutable/non-file targets; retain the already confirmed Stage 3 file-snapshot fallback only for its file shelf placement.
6. **Capabilities and one-operation focuses (direction confirmed; exact target matrix open):** `book` is the user-facing content interface and replaces separate `read`/`write`/`edit` tool calls with target-specific actions. Durable transcript/system/tool-call records are inspect-only; user/assistant chat edit is soft-forget, never physical erasure. A `book` operation against something outside the durable brain runs as a short, atomic, one-thing focus; when the caller is already in a focus, it performs the bounded operation inline rather than nesting another focus. Persist target identity/version/provenance and any durable finding before returning. `shell` remains focus-only. Project mutations still require their existing plan, approval, sandbox, network, and root checks; only the orchestrating context changes the plan.
7. **Return-time brain review (direction confirmed):** after a focus returns its report, prompt the continuing orchestrating context with an internal yes/no checkpoint asking whether the outcome should add or change anything in the shared atlas, ledger, or assessment. On yes, allow brain-scoped `book` operations before continuing; on no, proceed with the returned outcome. This is not a user-approval bypass, a second project task, or hard erasure. The external task remains ended; only brain-local updates are available at this checkpoint.
8. **Operation concurrency (version/idempotency confirmed; route consistency proposed):** use an explicit expected-version/precondition for edits and removals; reject stale writes with a fresh-state hint rather than overwriting. Repeating the same durable operation occurrence is idempotent; a genuinely new add creates a new entity unless that target's spec defines a natural-key upsert. Shelf removal addresses its placement ID, and unshelving removes only that placement. Recommended: terminal, screen, orchestrating, and focus routes share the same operation implementation/capabilities, with UI-specific presentation only.
9. **Migration and budgets (proposal):** migration is additive and restartable: preserve the store namespace and existing IDs, write mappings/tombstones separately from project source, keep old data readable until verified, and never expose content from a reference alone. Charge active context only for rendered selected content; full file snapshots remain backing storage. Keep temporary full schemas distinct from persistent shelf content, reserve schema headroom before provider submission, and reject or defer additions that cannot fit rather than silently dropping existing records.

Items 1–4, the version/idempotency rules in 8, and the focus/return directions in 6/7 are user-confirmed. The resolver status contract, cross-interface consistency, migration/budget policy, and initial capability matrix are adopted conservative defaults. The package-level feasibility trace supports the portable contract; provider-specific schema behavior and tokenizer headroom are verified when an endpoint is configured, with dynamic schema expansion disabled unless that endpoint is confirmed. This contract is frozen; no tests were run for the design trace.

**Proposed default capability contract (complete for review):** action names are semantic and target-specific; do not reintroduce generic user-facing `read`/`write`/`edit` tools. Project-file actions are `inspect`, `read`, `create`, and `edit`; no file delete/move action in the initial release. `create` requires a nonexistent path; `edit` names an exact file identity and expected content version, and both retain existing plan/approval/sandbox/network/root gates. ### 4A technical feasibility trace (package-level; no tests or 4B implementation)

Inspected the exact versions pinned in `package-lock.json` by unpacking the npm packages into temporary storage; no repository files were added by the inspection.

- **Durable IDs and call links:** `@earendil-works/pi-durable@1.5.2` defines branded numeric `ConversationId`, `EntryId`, `TaskId`, `SubmissionId`, and `DocumentId`. `DocumentId` identifies a Durable-managed document; it has no filesystem path/move behavior, so the confirmed Cartographer catalog adapter remains necessary. A model-issued tool call is represented by `ToolTaskInput { kind: "model", assistant: EntryId, callId }`; its durable execution task has a `TaskId`, and the result has its own `EntryId`. Nested `executeTool()` calls instead use `{ kind: "nested", parent: TaskId, parentCallId, key, call }`; their result is kept in the parent's `NestedCallDoc`, not as a separate transcript result entry. Therefore the confirmed model-call composite is sound, with a separate parent-task composite for nested calls.
- **Schema objects and local validation:** `pi-schema@1.5.2` builders return ordinary JSON Schema objects. `compile()` retains the schema for local validation; Durable's `prepareArguments` runs before its ordinary schema validation/execution. This supports preserving an exact schema object and its local validator as separate parts of a versioned tool record.
- **Provider-payload hook:** Durable's `beforeProviderRequest` receives the resolved model and provider-specific payload after pi-ai builds it; a returned payload replaces that request's body only, and the hook runs again on retries. This can select/replace outgoing schemas without changing the registered tool list, but it is API-specific, is not itself an active-context message injection, and must inspect `model.api`. Cartographer's current hook only observes the payload (`engine.sending`) and returns no replacement.
- **OpenAI-compatible schema serialization:** `pi-ai@1.5.2` serializes each OpenAI-completions tool with its `name`, `description`, and `parameters`; absent strict transformation it passes the full parameter JSON Schema through. In strict mode it clones/transforms the schema and rejects constructs including `allOf`, `oneOf`, `not`, `if`, and `then`. The current `book` schema uses these constructs, so the strict path cannot carry it unchanged. Non-strict transport preserves these keys in pi-ai's payload, but a specific llama.cpp/llama-swap or other compatible endpoint may reject or ignore them; package inspection cannot establish a live server's behavior.
- **Current schema-size measurement:** constructing the registered current `book` tool and serializing its parameter schema yields 12,956 bytes (plus an 839-character tool description), roughly 3,239 tokens by the project's four-characters-per-token estimator. The four current book branches range from 2,150 to 5,221 serialized bytes. These are local estimates, not provider-token counts or measurements of the future universal schema. Dynamic schema headroom therefore still needs an endpoint/model-specific bound; a fixed context-window percentage alone does not guarantee room for the largest schema.

**Recommended 4A/4B boundary:** freeze the semantic reference/capability/dispatch contract first; treat the provider-specific schema trace and a conservative measured headroom rule as the last 4A exit check before 4B. The package-level trace supports the mechanism but does not certify the configured inference endpoint. Do not start identity/resolver implementation until the contract is frozen and that endpoint-specific check is complete. Tests remain deferred.

### Resolution, schema, and context behavior

- **Resolver contract proposed for freeze:** resolution returns `{ ref, kind, requestedVersion?, resolvedVersion?, provenance, actions, status }`; statuses are `live`, `stale` (a pinned version is not current), `deleted` (tombstone), `inaccessible` (permission/root gate), `unsupported` (known kind/action not supported), and `oversized` (requested selection cannot fit). Malformed/forged references return `invalid_reference`; conflicts return `stale_write` with the current version only if authorized. Resolution is metadata-only; content is returned only by an allowed `inspect`/`read`/target action or explicit shelf add. No stale mutable content is labeled current.
- **Versioning proposed for freeze:** persist the exact UTF-8 bytes of each prompt section and canonical JSON schema source; version is SHA-256 of those bytes, with entity ID, source path, authoring revision, and provenance retained separately. - **Budget contract default:** use model-reported `n_ctx` when available, else configured `contextWindow`; reserve `maxTokens` for output and keep at least 20% of the total window as additional safety headroom. Measure the complete rendered request, including all active tools/schemas, with the server's tokenizer when available. The current four-character estimator is only a fallback estimate, not a hard guarantee; until calibrated against the configured server, dynamic schema expansion is disabled. - Include a fresh state block for each focus, with a one-line `I am ...` purpose and current project/brain/plan state. This is now implemented in request dressing; verify it at final acceptance.
- Allow focus contexts to update shared books except the plan. Only the orchestrating context edits the plan. Preserve approved-plan, sandbox, network, and file-confinement checks. Session controls remain orchestrator-only and shell remains focus-only; this does not block an out-of-brain `book` operation from being dispatched to a short focus, nor a bounded inline operation when already focused.
- The `return.shelf` handoff adds a named file/reference to the focus shelf when absent and queues it for the shared shelf; capacity and target validity still produce actionable errors.
- Implement out-of-brain `book` dispatch as a short, atomic focus, with no change to plan/approval/sandbox/network/root gates. When a focus already exists, perform the bounded operation inline rather than nesting another focus; `shell` remains focus-only.
- After `return`, give the orchestrating context an internal yes/no checkpoint for whether to update the shared atlas, ledger, or assessment. On yes, allow brain-only `book` operations before continuing; on no, continue with the outcome.
- Add or update focused tests without running them yet.

**Exit:** a focus sees the live shared state, can keep durable knowledge, cannot edit the plan, and returns with an accurate report and shelf handoff; only context not kept is forgotten.
